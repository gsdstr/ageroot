# ADR-0006 architectural review

**Verdict: CHANGES REQUESTED.** The two-skill direction is sound. The accepted ADR needs explicit configuration, runtime, and migration contracts before implementation can be reviewed consistently.

Reviewed 2026-11-23, locally, by dispatched Codex worker `task_03c784cb636b`. This is a design review of the current ADR, not a claim that the proposed implementation already exists. No source or design files were modified.

## Findings

### F1 — High: Specify per-role replacement and behavior after target exhaustion

**Evidence:** `docs/adr/0006-orchestration-and-role-routing-skills.md:21` says “first match wins”; line 40 says iterate targets until a supported harness and model are found. `GLOSSARY.md:75` and `GLOSSARY.md:83` repeat these concepts without defining their interaction.

At least three incompatible implementations fit this text: choose the first file containing any roles; choose the first file defining the requested role and use only its list; or concatenate that role's lists across layers until an executable target appears. A local file containing only `builder` must not erase the team `reviewer`, and a one-item override must not accidentally inherit a second list item by index. Exhaustion also matters: a local list containing only an unavailable approved target could unexpectedly launch a global/default target if implementations continue across layers.

**Required change:** Resolve each canonical role independently. First layer explicitly defining that role replaces the entire role definition and its ordered `targets`; never concatenate or merge list entries by position. Missing role inherits from lower layers. Recommend that exhaustion of this selected list returns `unavailable` rather than silently reopening lower layers; users can include their fallback targets explicitly. If cross-layer fallback is desired instead, name and specify it as a separate policy, including where traversal resumes and how to prevent it. Define `targets: []` as explicit disablement, while null, a present role without `targets`, missing candidate fields, and wrong types are errors. Do not repair a partial `{model: ...}` candidate using another layer's harness: each target must be a complete pair.

Three user-authored layers plus built-in defaults is a reasonable hierarchy; call it that consistently. “Three-tier” followed by four numbered layers is a minor wording issue, not the underlying blocker. Also explain that a tracked team role intentionally outranks a global preference, so global settings affect only roles not defined above them.

### F2 — High: PATH detection cannot establish model availability or authorize runtime failover

**Evidence:** ADR line 40 promises a supported harness/model in the local environment; lines 43–45 offer `show`, PATH-based `setup`, and machine-readable `resolve`, without probe, error, timeout, or runtime-failure semantics.

An executable may be installed but unauthenticated; a model may be known but unavailable to the account; a request may fail temporarily; and a timeout may occur after an agent has changed files or started a remote task. These states cannot share one “try the next target” rule. An offline resolver also cannot truthfully guarantee remote model reachability.

**Required change:** Separate deterministic configuration selection from harness discovery, optional bounded readiness probes, and actual dispatch. Use adapter-defined statuses such as `missing`, `supported`, `unsupported`, and `unknown` with reasons. Skip missing executables and known unsupported models within the selected list; do not invent aliases for unknown model IDs. Unknown model availability should remain explicitly unverified until a safe probe or launch validates it. Define whether an unverified candidate is selectable; a practical default is to select it with an explicit unverified status, rather than rejecting every harness without a model-list API.

Only failures proven to occur before execution may trigger automatic traversal. Retry transient errors within a small, shared time/budget allowance; follow explicit policy for alternate targets. Authentication/access failures should produce actionable diagnostics and obey lifecycle access gates, not silently switch account or provider. An ambiguous launch/timeout requires reconciliation of the original dispatch before retrying elsewhere. Once execution starts, failover is a new controlled attempt with preserved artifacts, not another resolver lookup. Exhaustion returns nonzero and a machine-readable rejection trace; no “first installed CLI” escape hatch. `show` and ordinary resolution should have no network or execution side effects.

### F3 — High: Preserve capability and independent-review constraints during fallback

**Evidence:** `.agents/protocols/orchestration.md:23` requires the Reviewer to be orthogonal to Builder. `templates/orchestration/orca/RUNBOOK.md:53` requires model-family independence. ADR lines 28–40 define only independent per-role lists and do not retain this constraint in the new interface.

Both roles can resolve independently to the same fallback model or family when preferred harnesses are unavailable. A `resolve reviewer` call has no Builder assignment context. Existence of a harness/model does not prove the role's capability profile either.

**Required change:** Keep role authority, capability requirements, gates, and review-independence policy in `ageroot-orchestrate`; keep target ordering and factual target metadata in `ageroot-roles`. Before dispatch, the orchestrator validates assignments as a set and filters the review candidates against the actual Builder assignment. Expose ordered candidates or a constraint/exclusion mechanism so it can select the next eligible Reviewer. Define independence precisely: separate worker identity/context, and model-family distinction where policy requires it; different harness names alone do not establish independence. Unknown family metadata must not count as proven independence. If no eligible reviewer remains, block/escalate rather than weaken policy.

Owner remains a human authority outside executable role routing. Define the mapping between current title-case phase roles (`Builder`, `Reviewer`, etc.) and lowercase configuration keys to avoid lookup failures after extraction. Keep one authoritative machine-role enumeration, with a documented human Owner exception for lifecycle schemas.

### F4 — High: Root removal leaves an unassigned Orca adapter and hardcoded routing

**Evidence:** `packages/ageroot_core/distribution/manifest.py:87` defines a separate default `orca_adapter` component under `.agents/orchestration/orca`. `templates/core/.agents/AGENTS.md:44` and installed `.agents/AGENTS.md` point there. `templates/orchestration/orca/adapter.py:11` hardcodes role/harness assignments; its runbook lines 51–55 repeats concrete models and points at the protocol to be deleted.

Removing just the neutral `orchestration` component does not prune the root directory: `orca_adapter` recreates it. Removing both loses the existing adapter and advertised runbook unless another destination is chosen. Moving only the neutral templates also leaves concrete role routing duplicated outside `ageroot-roles`.

**Required change:** State explicitly whether the Orca adapter is retained and relocated or retired with a migration notice. A clean boundary is neutral lifecycle policy in `ageroot-orchestrate`, optional harness-specific execution adaptation outside its neutral contracts, and all concrete assignment lookup through `ageroot-roles`. Update source and installed instruction pointers together. Remove hardcoded adapter/runbook assignments or mark them as nonauthoritative examples. Detection of `orca` must not itself select Orca supervision: execution mode still follows explicit owner/task intent. Orca's supervisory surface and its underlying worker harness/model need an explicit adapter mapping; the pair `{harness: orca, model: ...}` is not self-explanatory.

### F5 — High: Manifest-only pruning breaks existing checks and needs a state-aware migration

**Evidence:** `scripts/test.sh:12` unconditionally runs `scripts/sync-orchestration-package.py --check`; that script's lines 12–14 name the old source and target. `packages/ageroot_core/tests/test_distribution.py:29` and line 30 assert old neutral and adapter paths. Line 39 explicitly selects component names `orchestration` and `orca_adapter`. `distribution/collector.py:71` rejects unknown component names. `distribution/service.py:88` hardcodes `.agents/orchestration` among managed prefixes. `.agents/ageroot.state.yaml:18` onward records the old payload and snapshot paths.

Thus the answer to compatibility question 5 is **yes**: removing the directory/component without related changes breaks scripts/tests and potentially callers using explicit component selections. The update engine also deliberately treats previously managed paths absent from new renders as deletion candidates (`comparison.py:790`, `comparison.py:1279`); locally modified old files block deletion. Editing the manifest does not by itself safely migrate an existing installation.

**Required change:** Include sync tooling, the test runner, distribution tests/CLI examples, drift-prefix handling, state/snapshot transition, and published component-name compatibility in the migration plan. Choose whether old component names become deprecated aliases or are rejected with a documented upgrade path. Move/remove the canonical source protocol under `templates/core/.agents/protocols/`, not just its installed copy: the recursive core rule would otherwise redistribute it. Replace old drift coverage with coverage for each newly managed skill root; do not flag unrelated user-installed skills.

Use the existing dry-run/apply machinery for old managed-file removal, including deletion confirmation and locally modified file protection. Do not manually erase old state entries to make a check pass. Add upgrade cases for a clean prior installation, modified old payload, missing baseline snapshots, and retained unrelated local files. Document a short compatibility shim or a deliberate breaking release for external invocations of the old validator path. Update `GLOSSARY.md:125`, which still defines the portable package as an exact copy under the removed location.

### F6 — Medium: Standalone portability requires an explicit parser contract

**Evidence:** `SimpleYamlHelper` lives inside `packages/ageroot_core/comparison.py:136`. ADR-0005 wraps the Update engine and therefore legitimately depends on that package; `skills/ageroot/scripts/ageroot.py:13` adds repository/installed package roots to `sys.path`. The neutral validator already uses JSON-compatible YAML through stdlib `json` (`templates/orchestration/v1/scripts/validate.py:34`).

Direct parser checks confirmed that `SimpleYamlHelper` parses ADR's block-style list correctly, but parses `targets: [{harness: codex, model: example}]` as a string and silently accepts duplicate `builder` definitions, retaining the last. It is a limited helper, not a validating general YAML implementation. Silent syntax/key acceptance can select a different target than the author intended.

**Recommendation:** For the stated requirement that this skill run independently anywhere, avoid importing `ageroot_core.comparison` or relying on ambient `PYTHONPATH`. Ship a skill-local stdlib parser/validator with a deliberately narrow documented block-style YAML grammar, or explicitly adopt JSON-compatible YAML using `json` as the parser. The latter is simpler and matches existing validator precedent but changes the illustrated authoring syntax. Do not promise arbitrary YAML while implementing a subset. A general YAML dependency is a separate packaging decision, not an accidental import through the update engine.

If a restricted parser is chosen, reject unsupported flow syntax, duplicate keys, aliases/anchors/tags, invalid indentation and malformed scalars with file/line diagnostics. Validate version, root shape, canonical roles, candidate shape, and nonempty string fields before resolving. Missing files are normal; malformed or unreadable present configuration must report an error rather than silently dropping to defaults. A shared parser source can be bundled at build/materialization time to avoid hand-maintained divergence, provided runtime remains standalone. Test the installed skill outside the repository, without `PYTHONPATH`, with a fresh working directory.

### F7 — Medium: Define installation ownership and dependencies for both skills

**Evidence:** ADR-0005 decision 1 explicitly deploys the management skill using APM. `apm.yml:8` and `templates/core/apm.yml:8` declare it. ADR-0006 line 51 only adds the new skills as distribution components, while `GLOSSARY.md:314` describes APM materialization and `.gitignore:8` ignores installed skills. The current first-party memory skills show a distribution-owned exception, but its opt-in ownership is explicit in the manifest.

**Required change:** Choose and document which mechanism owns each installed path: APM, distribution, or a deliberately coordinated arrangement. Avoid independent APM materialization and generated-payload updates racing over the same skill directory. If following ADR-0005, add local and consumer APM dependencies with appropriate lock updates; if following distribution-owned memory precedent, state that exception and its update behavior. Specify default/optional components and dependency behavior when `ageroot-orchestrate` is selected without `ageroot-roles`. Discovery instructions must remain useful when skills are absent and explain how to install them.

### F8 — Medium: Workspace discovery, setup writes, and resolve output need stable contracts

**Evidence:** ADR lines 42–45 describe commands without workspace-root, overwrite, output-version, or exit-code behavior.

Running from a nested directory or child worktree must not create a second accidental `.agents` tree or read some unrelated current working directory. Global path handling should state whether the literal home path or `$XDG_CONFIG_HOME/ageroot/roles.yaml` wins. Auto-generated full role matrices can also freeze a local override for every role, hiding later tracked team updates.

**Required change:** Offer explicit `--workspace`/`--root`, and define deterministic discovery from the invocation location when absent, including nested worktrees and no-workspace behavior. `setup --global` must work outside a repository; workspace setup must fail clearly if no root can be identified. Preserve existing user configuration by default, generate only intended role overrides, and require an explicit overwrite option for replacement. Validate before an atomic write, support noninteractive input/dry-run, and report which destination changed. Detection must not execute arbitrary configured command strings; fixed adapter commands should use argument arrays without a shell.

Version the JSON response and define stable success, disabled, unknown-role, invalid-config, and unavailable results. Include selected role/target, source file/layer, candidate index, readiness level, and rejection diagnostics; print diagnostics to stderr and keep stdout parseable. Keep paths to executables as metadata distinct from configured harness identities. Built-in defaults should be visible and versioned; setup should not claim detection of exact model access from executable presence.

## Direct answers to the six review questions

1. **Architectural soundness:** Accept the separation in principle. Lifecycle policy, role authority, budgets, gates, schemas, and independent review belong to `ageroot-orchestrate`; target configuration, candidate ordering, adapter metadata, and resolution belong to `ageroot-roles`. A small versioned interface connects them. Current ADR does not completely allocate the existing Orca adapter, capability policy, or installation ownership.
2. **Config resolution:** Use role-level inheritance and atomic replacement of each role's ordered list. Missing role inherits; partial targets are invalid; explicit empty list disables. Recommend no implicit lower-layer traversal after an explicit role list is exhausted. Make unknown keys, duplicate roles, nulls, and invalid versions deterministic errors.
3. **Runtime resilience:** Traverse eligible targets only before execution, with bounded probes and recorded rejection reasons. Distinguish absence, unsupported model, unverified availability, authorization failure, transient errors, and ambiguous launch outcomes. Reconcile an ambiguous original launch before dispatching another. Preserve review independence and lifecycle gates across every fallback.
4. **Parser/dependencies:** Prefer a self-contained skill-local implementation under the portability objective. Use a strict documented subset or JSON-compatible YAML, not an unqualified miniature “YAML parser.” Reusing the existing helper is reasonable only if standalone installation is explicitly dropped and dependency discovery plus strict validation is specified; it is not equivalent to ADR-0005's intentional engine dependency.
5. **Backwards compatibility:** Yes, concrete scripts, tests, managed-prefix checks, instruction pointers, component selections, and tracked update state depend on old locations. F4–F5 identify the migration work. Existing tests passing now does not demonstrate proposed migration compatibility.
6. **Verdict:** **CHANGES REQUESTED**, for F1–F5 in particular. Resolve these contracts in the ADR before treating the extraction as implementation-ready; F6–F8 should become explicit implementation acceptance criteria.
